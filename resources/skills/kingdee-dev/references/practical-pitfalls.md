## 套打模板 PDF 实战

套打（打印）模板是高频需求，但官方文档语焉不详，实战坑点集中在 PDF 渲染与字段绑定。

**模板文件位置约定**：套打模板存于 `D:\AI\套打模板\templates\`；新增模板时通常复制已有配置（如 SO 销售订单 → 收款单）作为起点，再改字段，避免从零搭布局。

**字段绑定（电话 / 邮箱）**：
- SO 正式版通过 `ltxt_phone` / `ltxt_email` 文本控件绑定 `F_TRNV_Phone` / `F_TRNV_Email`；
- 启用 `autoAdjustHeight`（自动行高）避免长文本截断；
- 收款单模板额外加 `F_TRNV_ContactPerson.FName` / `F_TRNV_ContactPerson.FMobile`（联系人姓名 / 手机）。

**PDF 渲染常见坑**：

| 现象 | 原因 / 对策 |
|------|-------------|
| 文本被截断 | 单元格高度不足或未开 `autoAdjustHeight`；designer 改完需**重新保存（resave）**模板让改动生效 |
| 对齐错位 | `padding` 格式不一致；`cell-value` 基线差异（不同字段控件的默认值不同），需显式统一 |
| 改了不生效 | BOS 设计器 resave 后未重新发布；或浏览器缓存未清 |

**验证清单**：designer-resave → 检查 `padding` / `cell-value` 基线 → 启用 `autoAdjustHeight` → 重新发布 → 清缓存 → 导出 PDF 检查对齐、小数位、布局。

## HTML5 列表双分页机制

星空 HTML5 列表的分页是**两层**的，容易混淆：

| 层 | 机制 | 配置 |
|----|------|------|
| 服务端查询分页 | `TopRowCount` 控制每次从数据库取多少行 | 系统参数 / 列表服务端 |
| 客户端展示分页 | `viewOptions.pageSize`（默认 200）控制单页展示行数，对应 `ListFirstInRowCount` | 列表首次加载行数 |

**默认行为**：客户端单页展示 200 行（`ListFirstInRowCount` 默认 200）。
**自定义单页行数（如 400 行）**：研究 `ListFirstPageRowCount` 系统参数或调整 `ListFirstInRowCount`（必要时配合 `web.config`），使单页直接展示更多行，减少翻页。

> 排查「列表只显示部分行」时，先区分是服务端 `TopRowCount` 限制还是客户端 `pageSize` 限制，二者调法完全不同。

## BOS Designer 翻译不持久化 Bug

**现象**：在 BOS Designer 翻译平台填写的翻译内容，保存 / 发布后不持久化（下次打开为空或回退）。
**相关技术组件**：`LocaleValue`、BOS 设计器、元数据发布机制、`DynamicObject`、`PlugInProxy`、`ConvertEngine`。
**排查方向**：
1. 确认翻译写入的是 `LocaleValue` 而非临时缓存；
2. 检查元数据发布流程是否真正提交（签入 → 发布）；
3. 对比 `PlugInProxy` / `ConvertEngine` 在发布时是否覆盖了翻译字段；
4. 必要时在数据库层核验 `FLOCALEID=2052` 的 `_L` 表是否真正落库。

> 此 Bug 与版本 / 补丁强相关，定位后建议记录具体版本号与复现步骤，便于后续比对。

## 销售订单「客户-联系人」联动过滤

**需求**：销售订单选择客户后，联系人下拉只显示该客户的联系人。
**落地路径（全链路）**：
1. **可行性分析**：确认联系人基础资料与客户存在主从关系；
2. **源码排查**：定位过滤逻辑注入点（通常为表单插件 `DataChanged` 或字段的过滤条件）；
3. **插件实现**：在客户字段 `DataChanged` 后，动态设置联系人字段的过滤条件（关联 `F_TRNV_ContactPerson`）；
4. **SSMS 物理层佐证**：在数据库核对联系人与客户的内码关联（`_L` 表 / 关联表），确保过滤条件与物理数据一致。

> 关键点：联动过滤要在「界面交互」和「数据存储」两层都验证，避免选了联系人但保存后关联错乱。

## 预付款插件三种分摊模式

**插件**：`SAL_SaleOrderPrepayCalculatePlugIn`（销售订单预付款计算）。
**三种分摊模式**（枚举值）：

| 值 | 模式 | 说明 |
|----|------|------|
| 0 | 数量 | 按明细数量比例分摊预付款 |
| 1 | 瀑布 | 按顺序逐行分摊，直到分完 |
| 2 | 全额 | 按金额比例分摊 |

**重要业务规则**：**已结算行不再参与分摊**。
**财务视角差异**：订单级预付款分摊 ≠ 客户级 AR/AP。订单级只管单张订单内的行；客户级 AR/AP 看的是该客户跨单的应收 / 应付余额，二者不可混淆。

> 实现预付款分摊插件时，务必在 `OnPreparePropertys` 声明结算状态字段，并在分摊前跳过「已结算」行。

## 金蝶灵基（Lingee）调研要点

**定位**：灵基是金蝶推出的云星空客开插件开发平台（低代码 / 插件托管方向）。
**调研关注点**：
- **功能边界**：能覆盖哪些客开场景，哪些仍需传统 BOS 插件；
- **团队 / 组织架构 / 管理层**：评估其长期维护性与生态成熟度；
- **集成路径**：作为云星空客开插件开发平台的接入方式，与传统 C# 插件如何共存。

> 评估灵基时，重点对比「传统 BOS IDE + VS 插件」与「灵基平台」在开发效率、调试、部署上的差异，再决定是否迁移。
